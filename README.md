# AI 能量站 · AI Energy Hub

一个基于 **Python + SQLite + 原生 HTML/JavaScript** 的数字服务商城，提供 Apple 礼品卡充值与 AI 代充入口。前端采用暖白＋墨绿的简洁风格，无需 Node.js 构建或打包。

本 README 统一维护配置、部署、使用、升级、对账和回滚说明；开发者可另查 [源码入口](源码说明.md)。

> 本项目依赖现有上游 API，不是独立的商品供应或支付平台。部署前需准备可用的上游账户及对应业务能力；仅替换站名或账号，不代表商品、付款与履约链路已经完成验收。

## 部署前准备

1. **上游账户**：准备一套登录账号、登录密码和支付密码，礼品卡与 AI 代充共用该账户及钱包。这些是上游账户凭据，不是用户的 Apple ID 或 AI 账号信息。
2. **运行环境**：推荐 Docker Engine / Docker Desktop 和 Docker Compose v2；服务器需要 Git，并能访问上游 API、镜像仓库和 Python 包仓库。安装方式见 [Docker 官方文档](https://docs.docker.com/engine/install/)。
3. **正式访问入口**：准备域名与服务器，使用仓库提供的 Caddy 配置启用 HTTPS。
4. **客服图片**：将根目录 `contact-qrcode.jpg` 替换为自己的客服二维码，保持文件名不变。
5. **仓库访问权限**：如果仓库为私有仓库，先配置 GitHub 的 Git 认证，再执行克隆；不要把访问令牌写入克隆 URL、脚本或受版本控制的文件。

本地直接运行时建议使用 Python 3.11，与 `Dockerfile` 保持一致。Node.js 仅用于运行前端测试，不参与服务启动。

## 快速开始：Docker

以下命令均在 Bash / 兼容的终端中执行。

### 1. 获取代码

```bash
git clone https://github.com/witchan/ai-energy-hub.git
cd ai-energy-hub
chmod 600 .env
```

### 2. 填写配置

仓库已包含带逐项注释的 `.env` 空凭据模板。首次部署时直接打开它，填写共用的 `UPSTREAM_USER`、`UPSTREAM_PASS`、`UPSTREAM_PAY_PASS`，无需另建示例文件。已有运行配置时保留原值，按需合并新增参数，详见[环境变量配置](#环境变量配置)。

- 同时提供礼品卡与 AI 业务：保持 `ENABLE_GIFTCARD=1`、`ENABLE_AI=1`，只需填写上述一套账户。
- 只提供 AI 业务：设置 `ENABLE_GIFTCARD=0`、`ENABLE_AI=1`，仍填写上述三个共用参数。
- 只提供礼品卡业务：设置 `ENABLE_GIFTCARD=1`、`ENABLE_AI=0`，仍填写上述三个共用参数。
- 至少启用一种业务；启用业务的必填凭据缺失或启动登录失败时，服务会退出。

`.env` 的空凭据模板纳入 Git，Docker 构建上下文仍排除它。填写真实运行值后，Git 会显示本地修改；发布源码时三个账户字段保持为空，真实配置只保留在部署环境，不随源码提交。密码包含 `$`、`#`、空格等字符时，注意使用合适的引号；Compose 的单引号值按字面量处理，详见 [环境变量解析规则](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/)。

### 3. 启动并检查

```bash
docker compose config --quiet
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 shop
curl -fsS http://localhost:9006/healthz
```

健康检查应返回：

```json
{"code": 0}
```

浏览器访问 **http://localhost:9006/**。如果修改了 `.env` 中的 `PORT`，同步调整访问地址及 `PUBLIC_ORIGIN`。

**默认 `9006` 端口只绑定宿主机 `127.0.0.1`**，所以其他电脑直接访问“服务器 IP:9006”并不会打开网站。对外提供服务请继续使用下方 HTTPS 部署方式，而不是直接开放应用端口。

`/healthz` 仅确认应用 HTTP 服务可响应，不代表上游余额、商品库存或实际支付流程已通过检查。

## 环境变量配置

工程根目录的 `.env` 随源码提供，三个必填账户字段默认留空。首次部署直接编辑该文件；下面的配置与仓库模板使用相同参数和值，已有运行配置时按需核对，不要整份覆盖。

```env
# 上游 API 根地址；更换时需兼容现有接口。
UPSTREAM_BASE=https://likayi.com/api/v1
# 是否启用礼品卡业务：1 开启，0 关闭。
ENABLE_GIFTCARD=1
# 是否启用 AI 代充业务：1 开启，0 关闭；至少开启一种业务。
ENABLE_AI=1
# 两种业务共用的上游登录账号；必填。
UPSTREAM_USER=
# 共用上游登录密码；必填，不是客户的账号密码。
UPSTREAM_PASS=
# 共用上游支付密码；必填，两种业务从同一钱包扣款。
UPSTREAM_PAY_PASS=
# 礼品卡价格调整百分比：3 加价 3%，-3 优惠 3%；调整金额带符号向上取整到元。
PROFIT=3
# AI 代充价格调整百分比，规则与 PROFIT 相同；模板默认 0，即不调整。
AI_PROFIT=0
# 应用监听端口；更改后同步调整 PUBLIC_ORIGIN。
PORT=9006
# Docker 内监听地址；直接运行 Python 时改为 127.0.0.1。
BIND_HOST=0.0.0.0
# Docker 持久化数据库路径；直接运行 Python 时改为 ./data/shop.db。
DB_FILE=/app/data/shop.db
# 浏览器实际访问来源，包含协议和端口，不带末尾斜杠。
PUBLIC_ORIGIN=http://localhost:9006
# 是否信任反向代理的客户端 IP：直连用 0，可信代理后用 1。
TRUST_PROXY=0
# 仅使用 Caddy HTTPS 组合配置时填写域名，不含协议；本地 HTTP 可留空。
DOMAIN=
```

| 变量 | 用途与默认值 |
| --- | --- |
| `UPSTREAM_BASE` | 上游 API 根地址，默认 `https://likayi.com/api/v1`；更换地址时必须兼容现有接口和数据结构，并非任意 API 均可替换 |
| `ENABLE_GIFTCARD` | `1` 启用礼品卡业务，`0` 关闭；默认 `1` |
| `ENABLE_AI` | `1` 启用 AI 业务，`0` 关闭；默认 `1` |
| `UPSTREAM_USER` | 礼品卡与 AI 代充共用的上游登录账号；启用任意业务时必填 |
| `UPSTREAM_PASS` | 共用上游登录密码；启用任意业务时必填 |
| `UPSTREAM_PAY_PASS` | 共用上游支付密码，两种业务均使用同一钱包扣款；启用任意业务时必填 |
| `PROFIT` | 礼品卡价格调整百分比；`3` 加价 3%，`-3` 优惠 3%，`0` 不调整；支持小数，默认 `3` |
| `AI_PROFIT` | AI 套餐价格调整百分比；正数加价、负数优惠，支持小数；仓库模板为 `0`，完全未设置该环境变量时后端回退为 `3` |
| `PORT` | 应用监听端口，默认 `9006` |
| `DB_FILE` | Docker 使用 `/app/data/shop.db`，通过 `./data` 持久化；直接运行 Python 时改为 `./data/shop.db` |
| `BIND_HOST` | Python 直接运行使用 `127.0.0.1`；Compose 固定覆盖为容器内 `0.0.0.0`，宿主机发布端口仍只绑定回环地址 |
| `PUBLIC_ORIGIN` | 浏览器实际访问的协议、域名及端口，例如 `http://localhost:9006` 或 `https://shop.example.com`；不带末尾 `/` |
| `TRUST_PROXY` | 默认 `0`；仅在可信反向代理后使用 `1`，HTTPS 组合配置会自动设置 |
| `DOMAIN` | Caddy 使用的域名，例如 `shop.example.com`，不含 `https://` 或路径；HTTPS 部署必填 |

**旧配置迁移**：`AI_UPSTREAM_USER`、`AI_UPSTREAM_PASS`、`AI_UPSTREAM_PAY_PASS` 已不再读取。原来只配置 AI 账户时，将其账号、登录密码、支付密码迁移到对应的 `UPSTREAM_*` 参数，再删除旧项。两种业务共用一次登录和同一令牌缓存，业务开关与加价仍分别设置。

若旧部署使用不同上游账户，先在原配置下完成或核对各自的待处理订单，再切换共用账户；旧付款单和上游订单属于原账户，不要直接换账号继续查款或履约。

### 百分比加价 / 优惠与向上取整

- 礼品卡成本 = 面值 × 上游汇率 + 上游服务费；AI 成本 = 上游套餐人民币价格。成本先按人民币精度四舍五入到分。
- **调整金额 = 向上取整（成本 × 百分比 ÷ 100），售价 = 成本 + 调整金额。** 正数增加售价，负数降低售价；只将带符号的调整金额取整到元，不将最终售价整体取整。
- 填写 `3` 表示加价 3%，`-3` 表示按 3% 计算优惠，`-2.5` 表示按 2.5% 计算优惠，`0` 表示不调整；不要填写 `%` 字符。
- 成本 ¥99.50、加价率 3%：加价 ¥2.985 → ¥3，售价 **¥102.50**。
- 成本 ¥100.01、加价率 3%：加价 ¥3.0003 → ¥4，售价 **¥104.01**。
- 成本 ¥123.45、加价率 5%：加价 ¥6.1725 → ¥7，售价 **¥130.45**。加价恰为整数时不再多加一元。
- 成本 ¥100、设置 `-3`：调整 -¥3，售价 **¥97**。
- 成本 ¥99.50、设置 `-3`：调整 -¥2.985 向上取整为 -¥2，售价 **¥97.50**。沿用带符号金额的数学向上取整，实际优惠额会受整元取整影响；不是将优惠绝对金额取整为 ¥3。

后端使用十进制运算统一核算商品展示、下单金额和付款金额；前端直接使用后端报价，避免浮点误差导致多取整一元。礼品卡接口的 `profit_percent` 表示百分比，`quotes` 提供各面值报价，不再提供旧的固定金额 `profit` 字段。

礼品卡国家列表不展示汇率，卡片图标使用商品名称中的国家/地区旗帜；名称没有旗帜时检查地区字段，均没有时显示通用地球图标，不按货币符号猜测地区。报价中的 `original_price` = **面值 × `/site/country-rates` 返回的对应国家汇率**，不含上游服务费或百分比调整，按人民币精度四舍五入到分。这与商品采购汇率 `display_buy_rate` / `buy_rate` 是两套数据；右侧“原价”仍显示 `original_price` 与 `sell_price` 中较高的值。实际下单继续按采购汇率、服务费和原百分比规则计算，参考汇率不参与收款或履约成本计算。

商城国家列表隐藏土耳其礼品卡，由后端商品列表统一过滤，不依赖参考汇率是否成功加载；其他国家、AI 套餐和历史订单处理保持不变。

AI 代充列表展示上游所有已启用套餐（当前为 ChatGPT 4 款、Claude 2 款），无论库存都允许选择、下单和付款。所有套餐使用普通商品样式，不显示额外的库存或补货提示；`available_stock` 保留为上游数据，不参与前端卡片样式及本地下单条件，补货和履约由第三方平台处理。已下架、未启用或不存在的套餐仍不接受下单；未启用的套餐继续隐藏。价格及付款校验保持不变，确认付款后才创建上游代充订单，接口异常仍按原订单状态机制处理。

国家参考汇率通过后端从 `UPSTREAM_BASE` 下的公共 `/site/country-rates` 接口获取，不携带登录令牌。按商品名称中的国家或明确地区字段匹配，不根据 `$`、`€` 等符号猜测，避免美国/加拿大或瑞士等地区误配。商品接口增加 `reference_country`、`reference_rate`，原 `buy_rate` 含义不变。参考汇率缓存最多 5 分钟，刷新页面后获取当前报价；请求超时上限 5 秒，失败后间隔 30 秒重试。接口失败、数据过期或国家匹配缺失时，`original_price` 为 `null`，页面原价显示“暂不可用”，预估应付和下单照常；不会把采购汇率冒充参考汇率。

**从固定加价升级**：同样的 `PROFIT=3` / `AI_PROFIT=3` 现在表示 3%，不再是固定加 ¥3。核对目标百分比后重新加载配置或重建容器。新规则仅影响新报价和新订单；数据库中既有订单的金额及支付单不重算。

负数百分比直接生效，无需额外开关。旧的 `ALLOW_BELOW_COST` 配置已移除且不再读取，即使旧环境中仍为 `0` 也不阻止负数。百分比必须大于 `-100`，成本和最终售价必须大于 0。

优惠差额由商户余额承担；履约仍按上游完整成本检查余额，不足时订单等待商户补足余额，不会按优惠后的收款金额错误判断为余额充足。

## 正式部署：域名与 HTTPS

推荐在 Linux 服务器上使用 **Docker Compose + Caddy**。

### 1. 准备服务器

- 在服务器上完成前述克隆、`.env` 配置及客服图片替换。
- 将域名的 A 记录指向服务器公网 IPv4；若设置 AAAA 记录，也要指向可达的服务器 IPv6。
- 云安全组与服务器防火墙允许 TCP `80`、`443` 到达 Caddy，并确保没有其他服务占用这些端口。
- 组合配置还发布 UDP `443`，用于 HTTP/3；它不是基本 HTTPS 访问的必需条件。
- 服务器需要能访问证书签发服务。证书自动获取及续期条件见 [Caddy Automatic HTTPS](https://caddyserver.com/docs/automatic-https)。

### 2. 填写域名并启动

在 `.env` 中设置为自己的真实域名：

```dotenv
DOMAIN=shop.example.com
```

执行：

```bash
docker compose -f docker-compose.yml -f docker-compose.https.yml config --quiet
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.https.yml ps
docker compose -f docker-compose.yml -f docker-compose.https.yml logs --tail=100 shop caddy
curl -fsS https://shop.example.com/healthz
```

将示例域名替换为你的域名，访问 `https://你的域名/`。HTTPS 组合配置会覆盖应用环境为：

- `PUBLIC_ORIGIN=https://你的域名`
- `TRUST_PROXY=1`

Caddy 将请求反向代理给应用，并设置 `X-Real-IP`。证书与配置状态保存在 `caddy_data`、`caddy_config` 命名卷中；常规更新时保留这些卷。

**后续管理同一套 HTTPS 服务时，始终带上这两个 `-f` 参数**，避免误用普通 HTTP 配置重建应用。如果已有 Nginx/Caddy，应由现有入口管理 HTTPS，正确设置 `PUBLIC_ORIGIN`、可信代理及真实 IP，不要再启动一个争用 80/443 的入口。

## 本地 Python 运行

适合开发调试；先完成 `.env` 配置。`server.py` **不会自动加载 `.env`**，需要导出环境变量。

```bash
python3 -m venv .venv
. .venv/bin/activate
python3 -m pip install -r requirements.txt

set -a
. ./.env
set +a

# 覆盖 Docker 专用的数据库路径和监听地址
export DB_FILE=./data/shop.db
export BIND_HOST=127.0.0.1
export PUBLIC_ORIGIN="http://localhost:${PORT:-9006}"
export TRUST_PROXY=0

python3 server.py
```

这里只加载自己维护的 `.env`，且内容需要符合 Bash 语法，例如 `KEY='value'`。不要直接加载来源不明的 shell 配置；如果同一文件还交给 Compose 使用，确认特殊字符的引号在两种解析方式中都符合预期。

保持终端运行，然后打开 `http://localhost:9006/`。同一端口已有 Docker 服务或其他进程时，先停止该服务或在 `.env` 使用不同的 `PORT`。生产环境使用前述 HTTPS 部署。

## 使用部署脚本

[`deploy.sh`](deploy.sh) 支持本机 Compose 启动和通过 SSH/rsync 同步到远程服务器。

### 本机启动

```bash
./deploy.sh

# 或启用 HTTPS 组合配置；需要先填写 DOMAIN
HTTPS=1 ./deploy.sh
```

两种方式按需选一种，不需要连续执行。

### 同步到远程服务器

先在远端准备好**专用工程目录和 `.env`**，并确认：

- 本机与远端均可执行匹配的 Docker Compose 命令，且安装了 `rsync`。
- SSH 密钥登录和主机指纹核对已完成；脚本使用 `BatchMode=yes`，不会等待输入密码。
- 远端用户可以操作该目录和 Docker；`REMOTE_DIR` 使用不含空格的专用路径。

```bash
SERVER_HOST=203.0.113.10 \
SERVER_USER=deploy \
SERVER_PORT=22 \
REMOTE_DIR=/opt/ai-energy-hub \
SSH_KEY="$HOME/.ssh/id_ed25519" \
HTTPS=1 \
./deploy.sh
```

把示例主机、用户名和路径替换为自己的值。普通 HTTP 部署可省略 `HTTPS=1`。

脚本使用 `rsync --delete`：会清理远端目标目录内、本地已不存在的非排除文件，因此不要将它指向混放其他项目的目录。`.env`、`data/`、数据库文件、`.git/` 和 `artifacts/` 等被排除；**本机运行用 `.env` 不会通过该脚本上传**。Git 仓库提供的只是空凭据模板，首次远程部署时在服务器填写自己的配置，脚本更新不会覆盖它。

## 更新与备份

订单数据库默认位于宿主机 `data/shop.db`。升级前停止接收新订单，保管好 `.env`、数据库备份及 Caddy 持久化数据；旧进程和新进程不要同时处理同一个数据库。

`.env` 现在是受 Git 跟踪的模板，部署后填写的运行配置属于本地修改。拉取更新前将运行配置另行备份到工程外；若 Git 提示 `.env` 冲突，保留运行值并手工合并模板新增项，不用强制检出或重置来覆盖配置。

下面以 HTTPS 部署为例；普通 Docker 部署去掉第二个 `-f docker-compose.https.yml`。先确认镜像已经构建，命令从工程根目录执行：

```bash
# 停止应用；Caddy 可以保持运行，期间商城暂时不可用
docker compose -f docker-compose.yml -f docker-compose.https.yml stop shop

# 使用 SQLite backup API 创建一致性备份，不只复制单个 WAL 模式的 .db 文件
docker compose -f docker-compose.yml -f docker-compose.https.yml run --rm --no-deps -T shop python - <<'PY'
import os
import sqlite3
from datetime import datetime
from pathlib import Path

source_path = Path(os.environ["DB_FILE"])
assert source_path.is_file(), "数据库尚未创建或 DB_FILE 配置错误"
backup_path = source_path.with_name(
    source_path.stem + ".backup-" + datetime.now().strftime("%Y%m%d-%H%M%S-%f") + ".db"
)
source = sqlite3.connect(str(source_path))
backup = sqlite3.connect(str(backup_path))
try:
    source.backup(backup)
finally:
    backup.close()
    source.close()
print("数据库备份：", backup_path)
PY

# 拉取并重建；有本地改动时先处理改动，不要覆盖 .env 或 data/
git pull --ff-only
docker compose -f docker-compose.yml -f docker-compose.https.yml up -d --build
docker compose -f docker-compose.yml -f docker-compose.https.yml ps
curl -fsS https://shop.example.com/healthz
```

备份生成在 `DB_FILE` 同目录，默认会出现在宿主机 `data/`。完成后再将备份和配置保存在受控的异机存储，避免只保留一份服务器本地副本。常规升级不执行 `docker compose down -v`，以免删除 Caddy 命名卷。

### 从旧版本升级

1. 停止接收新订单并停止旧进程，按上面的步骤备份 SQLite。旧版本和新版本不要同时处理同一个数据库。
2. 更新代码、部署文件和依赖，核对[环境变量配置](#环境变量配置)。`PROFIT` / `AI_PROFIT` 使用百分比，不再是固定金额；旧的 `ALLOW_BELOW_COST` 已不再读取。切换共用上游账户前，先核对旧账户下的待处理订单，并确认 `PUBLIC_ORIGIN` 与实际访问地址一致。
3. 启动一个应用实例。迁移增加表和字段，保留既有上游关联及历史价格；旧版缺少履约状态的数据库中，失败且缺少上游订单 ID 的历史订单会转入人工核对。
4. 如果启动报历史充值单重复绑定，迁移会回滚并保留原记录。先逐笔核对，不要删单、改绑或删除唯一索引强行启动。历史空值或 0 只作为缺失编号占位，新订单必须保存有效的正整数充值单 ID。
5. 刷新所有已打开的旧页面，使用测试账户完成登录、商品、付款、账号提交和最终结果的小额闭环，再开放用户。付款查询须返回对应的 `data.id`、`data.status=1` 和匹配的 `data.amount`；字段缺失或金额不符时不进入履约。

### 代码回滚与数据恢复

上线前记录已验收的 Git 提交号，并单独备份数据库。历史复现记录和本地备份保存在工程外，不属于部署源码。

回滚时先停止接单和服务，在独立目录检出已验收的版本，核对配置与数据库兼容性后重新部署。**代码回退不会恢复数据库**；恢复数据库前先保留当前数据库副本、核对付款及处理中订单，再在停机状态执行恢复，不要用旧数据库直接覆盖正在运行的订单。

浏览器凭证存储也独立于源码回滚：旧页面只识别旧 `activeOrders` 数组，新版逐单记录不会因源码回退自动转换。回退前保留订单恢复链接，或使用仍兼容逐单存储的前端版本。旧版本可能缺少幂等和并发保护，先核对在途任务，不要把源码回退当成重新下单的方式。

## 上线验收与订单处理

正式开放用户前，使用自己的测试账户完成小额闭环：商品加载 → 报价 → 创建订单 → 付款确认 → 账号提交 → 上游最终结果。分别验证准备开放的业务，检查付款账户、金额和客服入口是否正确。

- 订单采用持久化状态控制，避免同一订单被并发重复提交给上游。
- 礼品卡与 AI 代充共用充值单唯一绑定：同一个有效 `recharge_id` 只允许关联一张本地订单，由 SQLite 唯一索引保证并发一致性。重复绑定返回 HTTP 409，不展示另一张订单的信息、不自动重试，也不增加随机金额尾数；取消、超时或完成后仍保留绑定。
- 新订单同时保存上游返回的 `recharge_no`，供商户与钱包流水的 `ref_no` 对账；它只作内部辅助字段，不显示给顾客、不替代 `recharge_id` 及付款状态/金额校验。历史订单或上游缺少该编号时留空，不自动补填；查询方法见下方[充值流水对账](#充值流水对账)。
- 上游创建结果不确定时，订单进入 `review` 人工核对，不会盲目再次扣款下单；先查上游记录，不要直接改回 `pending` 强行重试。
- 补交账号按 `credential_attempt_id` 标记每次提交，成功、失败和异常结果都只允许回写仍在等待该次提交的订单；后台已确认的处理中或终态不被迟到响应覆盖。上游 HTTP 5xx 即使返回有效 JSON，也按结果不确定处理，账号/验证码提交保持待核对而不重新开放重试。
- 用户应私下保存**订单恢复链接**；只有订单号不等于拥有订单访问凭证，恢复链接不要转发给他人。
- 浏览器以 `ai-energy-hub:order:<id>` 按订单独立保存凭证，并通过 `storage` / 页面聚焦事件同步；旧 `activeOrders` 数组保留并迁移至独立兼容键 `ai-energy-hub:legacy-order:<id>`，避免旧页面覆盖新凭证。最多加载最近 100 条，不主动删除更早的已保存凭证；存储不可用时仅保留内存，并提示用户保存恢复链接。升级后刷新所有旧页面。
- 本项目将账号信息最多暂存在进程内存中 15 分钟，履约时会发送给上游，并非只在用户浏览器本地处理；重启或过期后可能需要用户向原订单补交。上游订单 ID 会先落库，再提交账号信息；账号密码和 Session 不持久化到订单数据库。
- 付款二维码使用本地 `qrcode==8.2` 生成 SVG，不向外部二维码服务发送支付链接。付款检查使用前端单飞及后端持久化状态控制，后台查询不依赖付款弹窗持续打开。
- 项目未提供独立的商户管理后台或自动退款接口，异常订单与退款需要结合上游后台处理。

自动化测试使用模拟上游，不产生真实订单；测试通过不等于已经验证真实账户、实际收款或域名证书签发。

### 订单状态与异常核对

下表中的状态指 `fulfillment_state`，与第三方的数字订单状态 `status` 分开维护。

| 状态 | 含义与处理 |
| --- | --- |
| `pending` | 等待付款或商户补足余额，后台继续检查 |
| `dispatching` | 已持久化抢占，正在请求第三方下单；并发请求只返回处理中，遗留状态超过 5 分钟后转入 `review` |
| `created` | 第三方订单 ID 已保存，后台继续查询最终结果；缺少账号凭据时由用户向原订单补交 |
| `review` | 下单结果需要人工核对，先核对本地订单、上游账户、时间、金额及上游记录，再处理履约或退款；不要直接改回 `pending` 强行重试 |

上游尚无已验证的幂等创建/订单查询契约，因此请求结果不确定时不自动再发一次。人工核对和退款在上游商户后台进行，本项目没有自动退款接口。

付款弹窗倒计时为 5 分钟，倒计时结束或关闭弹窗不等于付款单已被上游撤销。后台会继续检查近期超时关闭订单的延迟付款，用户也可从原订单点击“重新检查付款”，不要另建订单来替代核对。

订单恢复链接的令牌放在 URL fragment 中，不随普通页面请求发送；持有者可以操作该订单，请私下保存。只有公开订单号而缺少访问凭证时，通过客服核对，公开接口不重新发放访问令牌。

### 充值流水对账

礼品卡与 AI 代充创建本地订单时，将上游充值响应中的 `recharge_no` 保存到 `orders.recharge_no`，供商户与钱包流水的 `ref_no` 辅助关联。该字段只从上游响应读取，不接受浏览器传入，订单创建响应、顾客订单查询和付款弹窗都不展示它。

它可为空，使用普通查询索引，不参与充值单唯一绑定，也不是付款成功的证据。付款始终核对本地保存的 `recharge_id`、上游成功状态和金额，不增加随机尾数。上游未返回、返回空白或非字符串时留空，历史订单也不自动补填。

在只读数据库连接中，将钱包流水的 `ref_no` 作为参数绑定为 `:ref_no`，查询对应本地订单：

```sql
SELECT order_no, order_type, recharge_id, recharge_no,
       sell_price, status, status_text
FROM orders
WHERE recharge_no = :ref_no;
```

## 常见问题

| 现象 | 检查方式 |
| --- | --- |
| 启动报“缺少必需环境变量” | 检查 `.env`、业务开关和对应账户；Python 直接运行要先加载环境变量，Docker 要从正确工程目录启动 |
| “上游登录失败”或商品加载异常 | 检查启用业务的账号密码、`UPSTREAM_BASE`、服务器外网连接和上游响应；不要把用户的充值账号误填成上游账户 |
| HTTP 403 / 来源校验不通过 | `PUBLIC_ORIGIN` 必须与浏览器实际来源一致；`localhost` 与 `127.0.0.1` 不相同，HTTP 与 HTTPS、不同端口也不相同 |
| 公网访问 IP:9006 不通 | 属于默认回环绑定行为；通过配置好的 HTTPS 域名访问 |
| Caddy 证书失败或 502 | 检查 DNS、80/443、防火墙、端口占用，以及 `shop` 健康状态；查看 `shop` 和 `caddy` 日志 |
| Python 报 `/app/data` 路径错误 | 这是 Docker 路径；直接运行时将 `DB_FILE` 改为 `./data/shop.db` |
| 修改 `.env` 后未生效 | 用原来的 Compose 文件组合重新执行 `up -d` 重建受影响容器；仅 `restart` 不会重新载入容器环境；直接运行 Python 则重新加载环境并启动进程 |
| 修改前端或客服图后未生效 | 文件通过 Dockerfile 复制进镜像，需要 `up -d --build`；不是宿主机文件实时挂载 |
| 提示容器名 `proxy-shop` 已存在 | Compose 当前仍固定使用该容器名，这是兼容旧部署的名称；核对已有容器归属，避免同时启动两套生产实例 |
| 订单长期处理中 / `review` | 核对上游是否已创建订单或扣款，再处理履约或退款；避免反复下单 |
| “付款单已关联其他订单” / HTTP 409 | 本次未创建新的本地订单。核对第三方是否返回了已有充值单；有原订单恢复链接时通过原订单查询，否则联系客服，不要用改金额或改编号绕过校验 |
| 启动报“历史订单存在重复充值单绑定” | 迁移已回滚，原订单记录保持不变。先备份数据库并逐笔核对上游付款、履约和本地订单；不要自动删单、改绑或删除唯一索引强行启动 |
| 换设备看不到订单 | 打开该订单已保存的恢复链接；缺少访问凭证时通过客服核对，不通过公开订单号重新领取凭证 |

排查时优先使用 `docker compose config --quiet` 校验语法；完整 `config` 输出可能包含环境变量，不要把含密码、Session、订单恢复令牌的配置或日志直接发到公开渠道。

## 并发修复与升级说明（2026-10-25）

- **下单幂等**：两个 HTTP 创建接口必须带 `Idempotency-Key`（浏览器用安全随机数生成的 64 位小写十六进制字符串）。SQLite `checkout_requests.key_hash` 唯一主键先原子占位，再创建第三方充值单；本地订单和幂等完成状态在同一事务提交。相同键与相同商品/面值重试返回原订单、原价格和相同访问凭证；同键不同商品/面值返回 409。请求仍在处理中、发生超时或结果不确定时返回待核对，不再次创建第三方充值单。
- **凭证和重试**：幂等键属于私密下单凭证，避免放入 URL 或日志。服务器只保存键的 SHA-256 摘要，不保存明文键或明文访问 Token；重放凭证从原随机键按独立用途派生。浏览器将键与商品选择存入 `sessionStorage`，不保存账号、密码或 AI Token。网络重试和同一标签页刷新后使用原键；存储不可用时保留内存并提示用户保留页面。已经成功创建后再次购买相同商品，需明确确认“另下一单”；取消则打开原订单，已付款订单展示进度而不再次提示付款。
- **幂等边界**：相同键表示同一次下单意图；不同键仍允许独立购买同样商品。两个独立新标签页并不自动视为同一订单，第三方调用方重试必须复用原键。重试不会覆盖第一笔订单暂存的账号，后续补交走已鉴权接口。无键的 `create_local_order()` 仅保留内部兼容，HTTP 入口强制校验键。停留在 `creating/review` 的记录需人工核对，切勿删除后盲目重试。
- **查款合并**：`payment_check_id/payment_check_until` 在数据库中认领同一订单的查询，跨进程的重叠请求直接返回当前已落库状态，而非等待或再次查询上游。完成/异常后释放，崩溃遗留租约 180 秒后可重新查询。它只合并重叠查询，不缓存付款结论；稍后的轮询仍会检查新付款。
- **后台调度**：常驻线程池最多 5 个工作线程，非阻塞 tick 不等待最慢订单；数据库工作租约同时限制共用同一个数据库的进程总计最多 5 个未过期活动任务，不无限排队。任务结束后安排 15 秒后的检查，崩溃遗留工作租约 600 秒后可恢复。慢上游占满 5 个槽位时仍会延迟处理，线程池不是无限吞吐保证。
- **验证码挑战**：成功提交后持久化 `twofa_state=submitted`，重复 true、缺少标志以及 false→true 都不自动重新开放；上游只返回布尔值，不能据此证明是新的挑战。明确拒绝仍允许重试，结果不确定保持 `review`。真正的新一轮验证需商户核对平台状态后再处理；未增加前台强制重开接口。`twofa_attempt_id` 和状态条件保护迟到结果不覆盖终态或待核对状态。
- **升级与回退**：迁移只增加表和可空/默认值字段，不重算历史价格、不改 `.env`。升级后刷新全部旧页面；旧页面缺少幂等键会收到 400。源码回滚不回退数据库或浏览器存储；旧服务器会忽略幂等键且丢失这些并发保护，实际回退前应停止接单并先核对处理中任务。恢复链接仍应由用户私下保存。

本轮原始 10 项审计复现全部通过，回归测试为 147 项后端与 42 项前端。测试使用临时数据库和模拟上游，不代表真实支付链路或长期高负载已完成验证。SQL 常量拼接与最终售价超限两个原 P0 误报未触发业务代码改动；价格规则和充值单唯一绑定继续保留。
